## Summary

Cart authors a great harness and stops there — its rules (the `/checklist` security
walk-through, every item's `Verify` field, `/build`'s deploy-verify) are *prose the agent
performs by hand*, while the one place Cart already runs an **enforced** harness is `/vitals`
(eight deterministic structural checks with remediation-style suggestions). The move is to
take the `/vitals` mechanic — deterministic check + error-message-as-remediation-prompt —
and point it at the *built app* instead of only the plugin install, then climb the autonomy
ladder (parallel swarms, TDD green-loop, observability-as-context) on top of that floor.
Cart's own `/evolve` discipline — propose, never auto-apply — is the same disciplined-
scaffolding posture OpenAI describes; these amends extend it from "improve the tool" to
"enforce and instrument the user's codebase," without adopting the throughput-first merge
philosophy that's irresponsible at solo scale.

## Proposals (ranked by leverage ÷ effort)

### 1. Verify-fields and the security walk-through become deterministic checks whose failures read as remediation prompts

- **Maps to finding:** #1 (mechanical enforcers + remediation-as-prompt). Harness tier: **authored → enforced.** This is the single highest-leverage borrow in the comparison doc and the exact feedback loop Cart's `/build` lacks.
- **What changes:** Two surfaces, both prose today.
  1. `plugins/vibe-cartographer/skills/build/SKILL.md` — the per-item **Verify** step (Step-by-Step Mode #3; Autonomous Mode checkpoint #4) currently says *"ask the builder to run the app and tell you what they see."* Add a step **before** the human eyeball: the agent attempts to execute the item's `Verify` field as a deterministic command (the checklist five-field contract already requires `Verify` to be *"Run [command] and confirm [expected output]"* — see `skills/checklist/SKILL.md` line 186). When the command exits non-zero or the expected string is absent, the agent does NOT just report failure — it re-enters the build with the failure text framed as a remediation instruction ("Verify failed: expected `200` from `curl localhost:3000/search`, got connection refused — the dev server isn't running or the route isn't wired; fix before marking the item done"). Human eyeball stays as the fallback for items whose `Verify` is genuinely visual.
  2. `plugins/vibe-cartographer/skills/build/SKILL.md` "When the Checklist Is Complete" — the documentation & security review (planned as prose in `skills/checklist/SKILL.md` step 3, lines 167-173: secrets scan, dependency audit, `.gitignore` check, `.env.example`) becomes a small deterministic pass: a `scripts/security-check.js` helper (Cart already ships and runs Node helpers — `scripts/atomic-*.js`) that greps for hardcoded-secret patterns, confirms `.env` is git-ignored, runs the stack's audit command, and emits findings **as remediation prompts** ("`.env` is tracked by git — run `git rm --cached .env` and add it to `.gitignore` before this item is done"). The agent reads the helper's output and acts on it, exactly as `/vitals` reads its check findings and offers fixes.
- **Why it pays:** Turns the two softest gates in the whole workflow (per-item verification and the final security item) from agent-judgment-and-vibes into a deterministic loop that mechanically holds the line and feeds its own fix instructions back into context. `/vitals` already proves Cart can do this — checks #6/#8 surface drift and suggest the exact next step; this generalizes that pattern from the plugin install to the built app. Catches the leak-an-API-key and broken-route classes before "done," not after push.
- **Effort:** Medium, incremental. The `Verify`-execution change is a one-session edit to one SKILL. `scripts/security-check.js` is a small standalone helper; start with the two highest-value invariants (secrets-in-repo, `.env` tracked) and grow.
- **Risk / blast radius:** Touches `skills/build/SKILL.md` (highest-traffic SKILL) and adds a new `scripts/` helper. **CROSS-PLUGIN FLAG:** `vibe-sec` is a sibling plugin whose entire job is security review, and `vibe-test` owns test-gating. This proposal MUST defer to them via Pattern #13 (`guide/SKILL.md` anchored-complements table) when present — the deterministic security helper is the *fallback when no specialist is installed*, never a reimplementation. The comparison doc's own "what to skip" warns against duplicating sibling capability. The `Verify`-execution change also intersects the checklist five-field contract (`skills/checklist/SKILL.md` line 189, "this format is a contract with /build") — making `Verify` machine-executable raises the bar on how `/checklist` writes that field, so the two SKILLs move together. Both are within-Cart contracts, not the shared-schema contracts, so no `builder-profile` / `session-log` / `friction` schema impact.
- **Do-now slice:** Add a `## Mechanical verification (when the Verify field is executable)` subsection to the *proposal*'s scope and ship `scripts/security-check.js` as a **read-only, advisory** helper first — it runs, prints remediation-framed findings, exits 0 regardless (mirrors `vibe-test:gate`'s "exits 0, gate decides" discipline). No SKILL edit in the do-now slice; the helper is invocable manually and proves the remediation-prompt format before it's wired into `/build`. Smallest reversible thing shippable today.

### 2. TDD green-loop as an alternative `/build` mode

- **Maps to finding:** the TDD loop ([`docs/horizon/tdd-loop.md`](docs/horizon/tdd-loop.md)) + finding #1. Harness tier: **authored → enforced** (the test suite IS the deterministic gate; the watchdog + auto-rollback are the remediation loop).
- **What changes:** New `plugins/vibe-cartographer/skills/tdd-loop/SKILL.md` + `commands/tdd-loop.md` loader, OR an autonomous-mode flag on `skills/build/SKILL.md`. Per the brief: takes a `docs/spec.md` slice → generates failing tests committed first → inner loop (minimal code to pass one test → run FULL suite → commit on green) → auto-rollback on regression → watchdog hard-caps attempts → opens a PR with the iteration log. The brief (`tdd-loop.md` open question #5) already lands the right composition call: Cart owns the loop control; defer to `vibe-test` for runner detection and coverage via Pattern #13.
- **Why it pays:** This is the "set it and check in the morning" primitive Cart's toolkit doesn't have, and it's the cleanest enforced-harness win because the contract (the test plan) is deterministic and the loop literally cannot drift from it without flipping a test the watchdog catches. Directly kills the duplicate-toast bug class the comparison doc keeps citing — a parse error surfaces before any test runs; the loop exits clean.
- **Effort:** Full cycle. New SKILL surface + watchdog + rollback mechanism + PR opener; the brief explicitly warns a single-conversation fake produces fragile code.
- **Risk / blast radius:** New command = new SKILL.md + loader + the friction-triggers.md row + the anchored-complements table entry + `/vitals` check #1/#6 coverage (every new SKILL must be cross-referenced and friction-wired or vitals flags drift). **CROSS-PLUGIN FLAG:** deep `vibe-test` dependency (runner detection, coverage threshold, `vibe-test:gate`/`vibe-test:coverage`) — coordinate the Pattern #13 contract before building, and decide the brief's open question #5 (Cart SKILL deferring to vibe-test, vs `vibe-test:tdd-loop` extension). The auto-rollback mechanism (brief open Q#4: `git reset --hard` vs per-attempt branch) touches the user's git history — pick per-attempt branch to keep blast radius reversible.
- **Do-now slice:** None — needs a cycle. Do-now contribution: the do-now slice of Proposal #1 (executable `Verify` + advisory security helper) is the *substrate* the TDD loop runs on, so shipping #1 first de-risks this cycle.

### 3. Parallel agent swarms for `/build`

- **Maps to finding:** #3 (parallel swarms — [`docs/horizon/parallel-swarms.md`](docs/horizon/parallel-swarms.md)). Harness tier: **authored → instrumented** (the coordinator observes per-worktree state and escalates only at judgment points — the autonomy ladder). This is the "biggest gap" axis in the comparison's three-column table (axis #3, Execution model).
- **What changes:** Cart `/build` autonomous mode (`skills/build/SKILL.md` "Autonomous Mode") dispatches subagents **sequentially today** — one per checklist item, in order. The brief replaces that with: a Cart-time DAG analyzer that walks `docs/checklist.md` and partitions independent items (no shared file/schema/runtime dep); a coordinator agent owning the DAG; per-item implementer subagents each in their own git worktree (defer to `superpowers:using-git-worktrees`); an adversarial reviewer subagent that audits each diff for the Insights bug classes (duplicate identifiers, scope drift, wrong-directory commits, stale context); a sequential-merge-after-sign-off protocol. Likely a new `/swarm-build` command rather than a breaking change to `/build` (brief open Q#5, backwards-compat for sequential users).
- **Why it pays:** OpenAI's ~3.5 PRs/eng/day is the existence proof the architecture pays off; the brief notes the Architect Galaxy cycle already landed 15+ commits via dispatched implementer/reviewer subagents, so this is a structural extension of infrastructure Cart already uses, not a new primitive. Compresses a 13-17 item checklist from a full session to a fraction, with built-in adversarial review catching shipped bugs before merge.
- **Effort:** Full cycle (~v2.0). New primitives: coordinator/implementer/reviewer agent definitions, worktree management, DAG analyzer, merge protocol — each is a SKILL or hook on its own.
- **Risk / blast radius:** Largest of the set. New command surface; fundamental change to autonomous-build execution. **CROSS-PLUGIN FLAG:** the brief (parallel-swarms.md line 49) notes adversarial-review patterns may extend to `vibe-test` (tests as gate), `vibe-doc` (docs as gate), `vibe-sec` (security as gate) — framework-level coordination. The reviewer subagent must also inherit Tier-1 hygiene enforcement (brief open Q#6). Worktree storage decision (brief open Q#1) touches the user's repo layout. No shared-schema impact unless the swarm logs per-agent session entries — if it does, that's a session-log shape question to flag before building.
- **Do-now slice:** None — needs a cycle. The brief is already the `/scope` hand-off; this proposal's contribution is ranking it #3 (below #1 and #2) because it has the highest effort and the steepest blast radius, and it composes *on top of* the TDD loop (a swarm coordinator can dispatch tdd-loop sub-runs per independent item — `tdd-loop.md` line 41). Build the floor (#1), then the loop (#2), then the swarm (#3).

### 4. Observability-as-context in `/build`'s deploy-verify

- **Maps to finding:** #5 (observability-as-context / instrumented verification). Harness tier: **authored → instrumented** (the agent observes the running system to verify its own work). Adopt the *principle*, not OpenAI's full CDP + per-worktree observability machinery (explicitly on the comparison doc's "what to skip" list at solo scale).
- **What changes:** `plugins/vibe-cartographer/skills/build/SKILL.md` "Pre-handoff: Deploy verification" (lines 242-266) currently asks the *builder* to eyeball: *"Did the deploy land cleanly? Run the deploy command, paste the result. Are the new runtime artifacts reachable?"* — it even enumerates the exact ground-truth checks (`firebase functions:list` shows the right trigger, a curl returns 200, CI deploys the latest commit). Change: the agent **runs those queries itself** where it safely can — execute the listed deploy-state probes, assert the structured output, and feed mismatches back as remediation prompts ("`firebase functions:list` shows `searchHandler` with trigger `https` but the spec calls for `pubsub` — the zombie-shell footgun from the SKILL's own findings list; delete and recreate"). Keep the human in the loop for anything requiring credentials the agent doesn't hold or judgment calls; the SKILL already names the exact findings (zombie shells, memory floors, region mismatches, CI/local desync) — turn that prose checklist into queries the agent observes.
- **Why it pays:** Cart already wrote the *what to verify* (the deploy-verify section is unusually specific). The only gap is *who runs it* — moving from "ask the builder to paste the result" to "the agent queries and asserts" is the smallest possible step onto the instrumented rung, reusing prose that already exists. Closes the gap the comparison doc names on axis #8 (production-readiness: "ours is a checklist; theirs is queryable instrumentation").
- **Effort:** Medium; scope carefully (the comparison doc flags this one specifically). Start with the cheapest structured assertions — exit codes and `curl`/`functions:list`/CI-status output the SKILL already lists — not a log/metric pipeline.
- **Risk / blast radius:** Touches `skills/build/SKILL.md` deploy-verify only. Lower blast radius than #1-#3 because it's a within-section behavior change, not a new surface. **Risk to flag:** the agent running deploy/list commands against a user's real cloud project — these are read-mostly (`functions:list`, `curl`, CI status) but the agent must NOT auto-run anything mutating (re-deploy, delete the zombie shell) without explicit confirmation; keep mutations as remediation *prompts to the builder*, not auto-actions. No cross-plugin schema impact; `vibe-doc:check` (deployment readiness) is an adjacent sibling — defer to it via Pattern #13 if installed rather than duplicating its deploy-readiness logic.
- **Do-now slice:** Reframe the deploy-verify bullets in the *proposal* from second-person builder asks ("Did the deploy land?") to agent-executable assertions, as a documented spec the agent can follow today even before the SKILL ships it — i.e., the agent running a Cart build *right now* can choose to execute the `functions:list`/curl checks itself and report structured pass/fail. No SKILL edit required for the do-now; it's a behavior the build agent can adopt immediately under the existing prose. Smallest reversible thing.

### 5. Garbage-collection / a new `/tend` command for the user's built app

- **Maps to finding:** #4 (garbage-collection / drift agents — [`docs/horizon/self-healing-reliability.md`](docs/horizon/self-healing-reliability.md)). Harness tier: **authored → instrumented/enforced** (scheduled agent observes the app for drift from golden principles, opens small reversible refactor PRs). This is the operational-entropy loop the comparison doc (axis #6) says Cart's self-evolution stack doesn't cover — *Cart's loop improves the tool; this loop improves the user's codebase.*
- **What changes:** New `plugins/vibe-cartographer/skills/tend/SKILL.md` + `commands/tend.md`. Scans the *built app* (not the plugin) for deviation from "golden principles" — the project's own `docs/spec.md` conventions + architecture docs + any patterns established during `/build` — and proposes small, single-purpose, reviewable refactor changes. Mirrors `/evolve`'s discipline exactly: **never auto-applies**, surfaces a ranked list, builder approves item-by-item. The comparison doc names `/iterate` or a new `/tend` as the home; `/tend` is the cleaner call because `/iterate` is builder-driven feature polish ("what do you want to work on?") while `/tend` is agent-driven entropy cleanup ("here's what drifted from your own conventions") — different intents, different commands.
- **Why it pays:** Cart builds an app and then has no primitive for "the app's code drifted from its own spec/patterns over the last N iterations." Codex mimics existing patterns including bad ones, so drift compounds (comparison doc); the same is true of any Cart-built app after a few `/iterate` rounds. `/tend` pays the debt down continuously instead of letting it compound, and it reuses the entire `/evolve` propose-don't-apply machinery the user already trusts.
- **Effort:** Medium-to-full cycle. New SKILL surface; the "golden principles" extraction (what does this app's spec actually require?) is the hard part. The self-healing brief notes this is the most ambitious of the three briefs and could grow into its own plugin.
- **Risk / blast radius:** New command surface (same `/vitals` cross-reference + friction-wiring + anchored-table obligations as any new SKILL). **Risk to flag:** `/tend` proposes changes to the *user's app code* — `/evolve`'s hard rule is "never touch files outside `plugins/vibe-cartographer/`," and `/tend` deliberately inverts that (it edits the user's repo), so the propose-don't-auto-apply discipline is load-bearing and must be even stricter than `/evolve`'s. **CROSS-PLUGIN FLAG:** the self-healing brief frames the broader reliability layer (PreToolUse hooks, monitor agent, nightly cron) as possibly its own plugin (`vibe-reliability`) spanning all siblings — `/tend` is the Cart-scoped slice of that; if the bigger reliability layer gets built, `/tend` should compose with it, not duplicate. The brief also flags the friction-logger capture-hole (the orchestrator-context gap, `self-healing-reliability.md` line 65) as a prerequisite for the cron layer — out of scope for `/tend` itself but a known dependency for the full finding #4.
- **Do-now slice:** Ship `/tend` as **read-only drift detection first** — scan the built app against its own `docs/spec.md` + architecture docs, print a ranked drift report (banner-style, like `/friction` and `/vitals` already do), propose nothing, write nothing. That's the smallest reversible slice: it surfaces the entropy without touching the user's code, and the propose-and-apply half lands in a later cycle once the golden-principles extraction is validated. (Read-only first is exactly how `/vitals` shipped — diagnostic half before remedial half.)

## What this tool should NOT adopt (and why)

- **Throughput-first merge philosophy** (minimal blocking gates, flakes resolved by re-run not blocking). OpenAI says outright this is *only* responsible at agent throughput and *irresponsible at low throughput* — at Cart's solo/small-build scale, gates still pay for themselves. The comparison doc names this as the one place where blindly following the blueprint would hurt. Proposals #1-#2 deliberately go the *opposite* way: more deterministic gates, not fewer.
- **Zero-human-in-the-code-loop as a universal goal.** Cart's Learner mode, comprehension checks, and per-item verification are *features* for the audience (people learning to build), not deficiencies. The autonomy ladder in #3/#4 is opt-in escalation, not a replacement for human-in-loop — offer "leverage mode" vs "learning mode," don't sacrifice one. The comparison doc's axis #7 frames this as a philosophical inversion Cart should keep choosing.
- **Full CDP + per-worktree ephemeral observability stack.** OpenAI-scale infrastructure investment with no solo-scale ROI. Proposal #4 adopts the *principle* (the agent observes the running system) via cheap structured assertions, explicitly NOT the machinery. Don't let #4 balloon into building an observability platform.
- **Auto-applying any of this.** Every proposal here mirrors `/evolve` and `/vitals`: propose, show the diff/remediation, require explicit consent. The `/tend` proposal (#5) is the sharpest case — it edits the user's own repo — and must be *stricter* than `/evolve`, never looser. Mechanical enforcement (#1) means deterministic *detection* + remediation *prompts*, NOT deterministic auto-fixes to the user's app.
